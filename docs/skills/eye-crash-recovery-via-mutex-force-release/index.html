Eye crash recovery via mutex force-release

When Eye crashes and cannot restart due to AbandonedMutexException, force-release the 3 named mutexes via PowerShell .NET API, then restart Eye. Eye revival also auto-clears zombie Chrome processes it owned.

user/developer

Steps

  1. DIAGNOSE STEP 1 — Symptom: wkappbot consoles dead, cdp/a11y commands hang. Check: tail D:/GitHub/WKAppBot/bin/wkappbot.hq/logs/eye-guardian.log | look for last tick timestamp. If stale >60s, Eye+Guardian are both dead.
  2. DIAGNOSE STEP 2 — Confirm AbandonedMutex: tail latest eye.pid=*.log (sort by mtime). Look for 'AbandonedMutexException'. This means Eye held the mutex when it crashed and never released it — new Eye cannot start.
  3. DIAGNOSE STEP 3 — Confirm mutex still locked: PowerShell OpenMutex test. foreach name in (Global\WKAppBotEyeAlive, Global\WKAppBotEyeGuardian, Global\WKAppBotEyeSpawn): h=OpenMutex(0x100000,false,name); err=GetLastError(). FOUND=alive, err=2=released, err=5=held-no-access.
  4. DIAGNOSE STEP 4 — Find mutex names WITHOUT source: grep -n Mutex D:/GitHub/WKAppBot/csharp/src/WKAppBot.CLI/Commands/AppBotEyeCommands.cs -> line 437: EyeAliveMutexName=Global\WKAppBotEyeAlive, line 479: EyeGuardian, line 732: EyeSpawn. If source unavailable: strings binary won't work (.NET single-file publish) but OpenMutex trial-and-error works.
  5. FIX STEP 1 — Force-release all 3 Eye mutexes via PowerShell .NET: Add-Type MutexKiller { ReleaseMutex: Mutex.OpenExisting(name).ReleaseMutex(); Close() }. Returns: released=ok, closed-only=released but unsynchronized (still ok), not-found=already clear. Run for EyeAlive+Guardian+Spawn.
  6. FIX STEP 2 — Restart Eye: wkappbot-core.exe eye. Wait 3-5s. Verify: tail logs/eye.pid=NEWEST.log for EYE_TICK or EYE_LOOP entries. Verify mutex: OpenMutex(Global\WKAppBotEyeAlive) => FOUND means Eye is alive.
  7. FIX STEP 3 — Console auto-recovery: wkappbot consoles reconnect automatically once Eye IPC pipe restarts. Eye holds WKAppBotEyeAlive mutex for its ENTIRE lifetime. Eye death = pipe death = console death. Eye revival = pipe revival = consoles reconnect.
  8. CHROME ZOMBIE — When Eye dies, it abandons handles to Chrome child processes. These become zombies (Task Manager shows them, TerminateProcess returns ACCESS_DENIED). Fix: revive Eye first — Eye cleanup releases its Chrome handles automatically. If still stuck: wkappbot-core.exe taskkill --force <pid1,pid2,...> OR SeDebugPrivilege TerminateProcess via wkfix.ps1 -Kill <pid>.
  9. CHROME ZOMBIE ROOT CAUSE — Eye mutex AbandonedMutex blocks Guardian from spawning new Eye. Guardian sees 'already running (mutex not acquired in 3s)' and gives up. Solution: force-release mutex first, THEN restart Eye. Order matters.
  10. HANDLE SCANNER — wkfix.ps1 -ScanHandles <pid>: uses NtQuerySystemInformation(***), 16-byte header (NumberOfHandles+Reserved), stride=40 bytes per entry (SHX struct: Object+PID+Handle+Access+BT+TypeIdx+Attrs+Rsv), DuplicateHandle to current process, NtQueryObject(1=ObjectNameInformation) with UNICODE_STRING at nb+0(len)+nb+16(data). Filter by name substring.
  11. NUKE PATTERN — wkfix.ps1 -Nuke <pid>: enumerate all handles of target pid, DuplicateHandle with MUTEX_ALL_ACCESS(0x1F0001), call Win32 ReleaseMutex(dup) — succeeds only for Mutant type, skip others — then CloseHandle(dup), finally TerminateProcess with SeDebugPrivilege. One command to drain all mutexes + kill.
  12. CHROME SINGLETON — Chrome uses a named kernel object: \BaseNamedObjects\!device!harddiskvolume3!program files!google!chrome!application (path with backslash replaced by !, drive letter via QueryDosDevice C: -> \Device\HarddiskVolume3). NOT a Mutex (OpenMutex returns err=6=wrong type). NOT a FileMapping (same). TypeIdx=21 in this Windows version. Cannot be released by Mutex.OpenExisting. Kill Chrome process instead.
  13. SHORTCUT — wkfix.ps1 at D:/GitHub/WKAppBot/bin/wkfix.ps1: -EyeStatus (check mutex state), -Eye (release+restart), -Chrome (SeDebugPrivilege kill all debug-port chromes), -Nuke <pid> (drain mutexes+kill), -Mutex <name> (single release), -All (Eye+Chrome full reset). No reboot needed if mutex force-release succeeds.
  14. ROOT CAUSE SUMMARY — Three bugs filed as suggests 2026-05-07: (1) AbandonedMutex on crash: Eye should use try/finally to release mutex. (2) Guardian has no watchdog: if Guardian dies, Eye never restarts. (3) Eye not elevated: lacks SeDebugPrivilege so cannot kill/reap zombie Chrome children, causing zombie accumulation.
  15. FIND-OWNER PATTERN: zombie PID TerminateProcess fails -> do NOT hardcode Eye as culprit. Real owner = Win32_Process.ParentProcessId. Any wkappbot tool (wkchat, wkappbot-core, Eye, agents) could hold the handle.
  16. FIND-OWNER FIX: wkfix.ps1 -FindOwner zombie_pid -> get PPID via WMI -> Nuke(ppid): drain mutexes + TerminateProcess(SeDebugPrivilege) -> parent death releases child handles -> zombie gone. No full system handle scan needed.

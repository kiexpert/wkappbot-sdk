Opus files bugs and improvement ideas on sight -- aggressive wkappbot suggest filing standing order

When Opus (or any model) encounters a wkappbot bug, UX flaw, retry-prone pattern, unhelpful error, or improvement idea, file a wkappbot suggest IMMEDIATELY in the same turn. Do not batch, do not gate. Discovery context fades fast; queued bugs become lost bugs. User authorized aggressive filing 2026-05-29.

Steps

  1. Trigger: while using ANY wkappbot tool (skill add/edit, suggest, file edit, mail send, cdp, eye, slack, ask, claude-usage, etc.) you observe (a) a clear bug, (b) confusing/misleading UX, (c) a frequently-retried pattern, (d) an unhelpful error message, (e) a missing-but-obvious feature, or (f) a workflow that wastes user time. Do NOT mentally bookmark it; file it RIGHT NOW.
  2. Submit immediately, same turn, via wkappbot suggest (or wkappbot-core.exe suggest if eye blocks). Do not batch, do not wait for permission, do not let the discovery context fade. The discoverer is the only person with full context; queueing it = losing it.
  3. Body MUST be friendly and constructive (Opus tone): start with one-sentence BUG or FEATURE summary, then a clear FIX SPEC the SDK team can implement directly (what to change, where in the code if known, what the new behavior looks like). Include a PRECEDENT line citing the exact session/date the issue was hit -- gives the fixer a real reproduction anchor.
  4. Requirements (3 minimum): use the current-vs-proposed pattern. One "wkappbot X => current actual" line proving the bug, two "proposed: wkappbot X => after fix, expected" lines describing the target behavior. If the failing cmd is itself a not-yet-wkappbot subcommand, use proposed: for all three and put the validation snapshot in the body.
  5. Severity heuristic: a 2-3 retry burden on Sonnet/Opus already costs more tokens than 5 such suggests do to file. Anything that wastes a user retry cycle is high-severity. Anything that surfaces only after compaction or context loss is critical -- file immediately or it never gets filed at all.
  6. Do NOT pre-filter for "is this important enough". User has explicitly authorized aggressive filing (standing order 2026-05-29): bugs and improvement ideas get fixed fast only when Opus files them aggressively as it discovers them. File-then-prioritize beats think-then-maybe-file.
  7. Edge cases: (1) if the bug is in suggest itself (validator UX, draft-corruption, eye-block silent drop) use wkappbot-core.exe direct path. (2) if cmd parsing repeatedly mangles the body, see haiku-handoff-on-cli-retry and delegate the submit. (3) DGWCS cross-project resolve bug is known broken -- file past it, do not waste time on workarounds.
  8. After submit: paste back the suggest ts to the user in 1 line. No need to await acknowledgement -- the suggest is already durable in suggestions.jsonl. Move on with the original task.

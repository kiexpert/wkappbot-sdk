Launcher WKAPPBOT_CHROME_TARGET env + pipe protocol

Launcher publishes validated caller-offset Chrome placement target via WKAPPBOT_CHROME_TARGET env var AND forwards through Eye command pipe with __target prefix. Core reads same coords so SetWindowPos, post-launch stability loop, and per-command reposition all use Launcher-computed target. Without this Core falls back to ExpectedBounds (rightmost monitor anchor) and fights Launcher SetWindowPos producing wrong-monitor regression.

Steps

  1. PROBLEM: Launcher computes validated caller-offset target via TryMoveWebBotNearCaller then SetWindowPos. Core (separate process) re-derives target from caller HWND which can diverge -- Core ResolveCallerHwnd re-walks process tree and picks different ancestor with off-screen coords -- and falls back to ExpectedBounds (rightmost monitor 1740,20). Result: Chrome bounces between two positions per command.
  2. PROTOCOL PART 1 ENV VAR: After [PLACEMENT:VALIDATE] log in MyCdpContext.Placement.cs TryMoveWebBotNearCaller, set Environment.SetEnvironmentVariable WKAPPBOT_CHROME_TARGET to x,y,w,h string with DefaultChromeW/H matching Core CdpClient.OuterWidthPx/OuterHeightPx constants. Log [PLACEMENT:ENV] WKAPPBOT_CHROME_TARGET=x,y,w,h.
  3. PROTOCOL PART 2 PIPE FORWARD: In EyeCmdPipeClient.cs Send method, read WKAPPBOT_CHROME_TARGET env var and prepend __target:VALUE to JSON payload list (alongside __cwd and __hwnd prefixes). Eye-delegated commands forward this to Core which honors the same coords the Launcher SetWindowPos already applied.
  4. WHY BOTH PATHS: Direct RunCoreDetachedNormal path uses env var inheritance. Eye-delegated path uses pipe prefix because Eye spawns Core in separate context that does not inherit Launcher env block reliably. Both deliver the same payload.
  5. CORE-SIDE READER: Core ChromeLauncher.ComputePlacementNearCaller + CdpClient.SetWindowBoundsWaitStableAsync must check WKAPPBOT_CHROME_TARGET first before falling back to ExpectedBounds. The --window-position chrome.exe launch flag, post-launch stability loop, and any per-command reposition must all read SAME value.
  6. FORMAT: comma-separated x,y,width,height (e.g. 100,200,1400,900). Width/height are DESIRED final OUTER size (Chrome process window outer rect including chrome frame).
  7. FAILURE MODE: env var set wrapped in try/catch -- failure is non-fatal. Without env: Core falls back to ExpectedBounds and overrides Launcher placement. Diagnose via cdp-mon -- if TGT-POS pins to rightmost monitor anchor (1740,20) instead of following caller terminal then env var or pipe forward is missing.
  8. VERIFICATION: After hot-swap, run wkappbot ask gpt ping from terminal at known position, check cdp-state.jsonl for [PLACEMENT:ENV] line, verify TGT-POS in cdp-mon matches env var coords. Should change per terminal CWD/position.
  9. RELATED FILES: csharp/src/WKAppBot.Launcher/MyCdpContext.Placement.cs (env set) and csharp/src/WKAppBot.Launcher/EyeCmdPipeClient.cs (pipe forward). Commit 65c617fe introduced the protocol on 2026-05-16.
  10. PREFLIGHT FIX (2026-05-25): TryValidateAndCorrectPlacement now does a no-sleep preflight position read before the 5-attempt loop. If Chrome is already within threshold (attempts=0), Stage 2/3 watcher is also skipped. Result: cdp open on already-placed Chrome returns in <200ms instead of 750ms+

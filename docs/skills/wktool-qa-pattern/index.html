wktool QA pattern: token-efficient bug detection scripts

How to write wkask/wkcdp-style QA scripts that find bugs cheaply. Key principle: state-check first (fast), eval-js second (medium), DOM check last (slow). Auto-file suggest on confirmed bugs.

Steps

  1. PRINCIPLE: wk-tool scripts replace Claude polling logs. Claude reads ONE clean result. Scripts do the work. Token cost = near zero per check.
  2. STATE-CHECK FIRST (cheapest): before any CDP eval, check observable state -- TGT-POS from cdp-mon, file sizes, log tail. If off-screen (x<-100 or y<-100) = geometry bug = skip eval, auto-file suggest. No need to invoke Chrome at all.
  3. MINIMIZED RECOVERY (before eval): if Chrome window is minimized/iconified, restore it first via 'wkappbot a11y restore GRAP' then wait 2s. Minimized Chrome doesn't render pages -- DOM checks return false negatives.
  4. EVAL-JS (medium cost): use 'wkappbot a11y eval-js JS --grap {proc:chrome,cdp:PORT}' for DOM state. Keep JS under 200 chars. Return null for not-found so you can check with -notmatch 'null'. Example: document.cookie.split(';').length
  5. CROSS-VALIDATE heuristics: if you have a fast heuristic (SQLite file size, log keyword) AND a slower truth (eval-js), run both and compare. Mismatch = update the heuristic threshold. Log the mismatch as a warning.
  6. AUTO-SUGGEST on confirmed bugs: if off-screen/DEAD/mismatch is confirmed (not transient), call wkappbot-core.exe suggest with: exact port, observed value, expected value, and reproduction command. Use --requirement with wkappbot commands only.
  7. TIMING: cookie/DOM checks at session CLOSE (post-ask done) not during -- avoids noise during active processing. State checks (off-screen) can run any time via wkcdp.
  8. NAMING: wk<domain>.ps1 in D:/GitHub/WKAppBot/bin/. Subcommands via switch($Command). Default='status'. Add new checks as subcommands (cookies, cookies-test, etc.) not new scripts.
  9. TEST SUBCOMMAND: every wk-tool should have a '<tool> test' or '<tool>-test' subcommand that validates its own detection logic by cross-checking fast heuristic vs eval-js truth and reporting AGREE/MISMATCH.
  10. USER-PERSPECTIVE BASELINE: for public SDK regressions, cross-check against sdk-user-perspective-test-playbook before diagnosing internals; the user flow is the source of truth.
  11. TOKEN-SAVING WAITING: while a smoke test is running, do not busy-poll logs. Use the wait window to fix the next bug or tighten the next QA case, then read one clean result at the end.
  12. FASTEST VALID SMOKE FIRST: always look for the shortest trustworthy path (probe, one-shot, state check, or narrow harness) before long interactive smoke. Prefer the minimum command that proves the bug or fix.

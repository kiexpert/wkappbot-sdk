Safe Bug Fix Protocol -- before touching any working code

Checklist to prevent regression cascades. Read before fixing any BUG-AUTO or suggest. Core rule: understand WHY code exists before removing it.

user/developer

Steps

  1. RULE 0 — WHY before HOW: before touching ANY line of working code, read its comments and understand WHY it exists. If a comment says 'mixed-DPI drift fix', that IS the spec. Deleting code to make an error go away is NOT a fix.
  2. REPRODUCE FIRST: trigger the actual bug behavior before writing any fix. BUG-AUTO reports may be false positives (e.g. verification using wrong DPI scale). If you cannot reproduce it manually, do not change production code.
  3. MINIMAL SURGERY: change only the specific line causing the problem. If snap() fires with wrong timing → add delay. Do NOT remove snap entirely. If evidence check runs in --confirm path → add goto label. Do NOT restructure the whole method.
  4. TEST = RUN THE ACTUAL FEATURE: build success is NOT enough. Eye DPI fix → actually move Eye window across monitors and observe. Suggest resolve fix → actually run wkappbot-core.exe suggest resolve and read the output. No exceptions.
  5. RESOLVE ONLY AFTER VERIFIED: never close a suggest before step 4 passes. If you cannot test the feature (no HTS open, no secondary monitor), say so explicitly instead of claiming success.
  6. BUG-AUTO TRIAGE: check if actual=intended*(monitorDPI/96) before assuming drift is real. Check if error disappears after Eye restart (stale binary). Check if it is cross-channel false positive before filing or fixing. Most BUG-AUTO Eye DPI drift reports in 2026-04-30 were caused by snap removal, not a real bug.
  7. WPF DPI CONTENT SCALING: SetProcessDpiAwareness(2) alone is NOT enough for WPF content to rescale on monitor boundary. WPF reads app.manifest at startup to set its rendering DPI mode. Without <dpiAwareness>PerMonitorV2</dpiAwareness> in app.manifest, WPF uses system DPI for layout until WM_DPICHANGED fires (visible transient wrong-scale glitch). Fix: add dpiAwareness + dpiAware to app.manifest windowsSettings. This is a separate concern from snap position correction (AnimateMoveTo).

  9. NEVER touch app.manifest dpiAwareness for Eye DPI fixes. PerMonitorV2 manifest changes WPF coordinate semantics globally -- Window.Left/Top units change, hover detection breaks, window sizing changes, hundreds of coord-dependent paths break. SetProcessDpiAwareness(2) in code is sufficient. The Eye snap formula uses Window.Left as physical pixels (system-DPI app); do NOT multiply by GetDpiForWindow() -- that double-scales when system DPI=96.

  13. ScreenCoords (ScreenCoords.cs) is the ONLY approved class for WPF↔physical pixel conversions. Methods: PhysicalToLogical(physX, physY, hwnd) uses per-monitor DPI; PhysicalToLogicalSystemDpi(physX, physY) uses system DPI for WPF Window.Left/Top; LogicalToPhysical(logX, logY, logW, logH, dpiScale) converts WPF logical to screen pixels. Rule: NEVER use GetDpiForSystem() directly for coordinate math -- always go through ScreenCoords. Multi-monitor: use _liveDpiScale (computed by CalcCalloutGeometry for that monitor) when converting callout window bounds. If a LogicalToPhysical overload is missing, ADD it to ScreenCoords rather than doing inline math.
